# 后续扩展方向

ACMP 当前已经建立“资源事实—规格—配额—推理部署—监控”的主链路。后续扩展应建立在这条链路之上，避免创新功能脱离真实资源和监控数据。

## 1. 扩展原则

- 不改变 Kubernetes、HAMi 和 Prometheus 的职责边界；
- 新模块优先消费现有数据，不重复采集和保存全部时间序列；
- 仿真结果先用于辅助决策，不直接改变生产集群；
- 继续保持单管理员 MVP，验证价值后再增加复杂权限和自动化；
- 每项能力都应有可演示的输入、过程和输出。

## 2. 创新实验室定位

创新实验室不是新的资源管理入口，而是利用现有监控和部署数据进行分析与仿真的实验区。

它由三个独立入口组成：

```text
负载感知
  → 数字孪生
    → 策略仿真
```

三者使用保存的快照衔接，避免仿真过程直接依赖实时生产状态。

## 3. 负载感知

负载感知用于建立某个推理服务的业务负载基线。

用户流程：

1. 选择租户、项目和推理服务；
2. 选择监控时间范围；
3. 选择银行大模型业务类型；
4. 读取 Prometheus 和 vLLM 原始指标；
5. 展示负载曲线和模式判断；
6. 保存负载感知结果，生成可供仿真使用的负载文件。

银行场景可优先覆盖：

- 智能客服：工作时段周期和突发咨询；
- 知识问答：相对稳定但存在批量活动；
- 风险审查：批处理和时限要求；
- 办公助手：日间周期明显；
- 营销活动：短时峰值明显。

最小输入包括请求速率、输入/输出 Token、延迟、队列和 GPU 利用率。

## 4. 数字孪生

数字孪生将一次负载感知结果与模型、算力和故障条件组合成可重复的仿真基线。

用户选择：

- 负载快照；
- 模型快照；
- GPU 资源快照；
- 一种负载注入；
- 一种故障注入。

MVP 中建议保留最关键的两类注入：

- 负载注入：指定时间将请求量放大到某一倍数；
- 故障注入：指定一张 GPU 或一个 Worker 暂时不可用。

数字孪生保存的是仿真输入，不需要把 Prometheus 全部原始时间序列拆成大量数据库表。快照和事件可以先使用结构化 JSON 保存。

## 5. 策略仿真

策略仿真基于同一个数字孪生基线，对比：

- 平均分配；
- 利用率优先；
- 成本优先；
- SLA 优先。

输出重点包括：

- P95/P99 延迟；
- SLA 达标率；
- 吞吐量；
- GPU 利用率；
- 排队时间；
- GPU 卡时或成本估算；
- 故障后的恢复效果。

用户看到的是多策略对比和解释，不是一个自动替用户修改生产调度的按钮。

## 6. SimAI 接入

SimAI 适合作为独立仿真执行器，而不是嵌入 Spring Boot 进程。

建议链路：

```text
ACMP 保存快照与策略
  → Adapter 生成 SimAI 输入
  → Kubernetes Job 运行 simai-runner
  → 生成统一结果文件
  → ACMP 保存摘要
  → 前端展示 KPI 对比
```

Adapter 负责把 ACMP 的负载、模型、资源和故障事件转换为 SimAI 配置。这样后续升级 SimAI 不会直接影响核心业务模型。

详细设计参考：

- `docs/14-SIMAI-INTEGRATION-DESIGN.md`
- `docs/19-INNOVATION-LAB-SIMAI-MVP.md`
- `docs/lab.md`

## 7. 监控数据向实验数据转换

Prometheus 继续保存原始指标，创新实验室只保存：

- 所选时间范围；
- 聚合后的关键曲线；
- 负载模式和判断结果；
- 模型与资源快照；
- 注入事件；
- 仿真结果摘要和原始结果文件位置。

这避免数据库成为第二个 Prometheus，也便于同一快照重复运行不同策略。

## 8. 其他可扩展方向

### 8.1 更多 GPU 品牌

通过品牌适配表扩展：

- 设备资源符；
- 型号和显存发现规则；
- 监控 Exporter 和指标名称；
- 独享与共享调度参数。

核心资源池、规格和租户配额模型不需要随品牌重写。

### 8.2 模型存储

当前使用 Node 本地 `hostPath`。后续可按实际环境增加：

- NFS；
- CephFS；
- 对象存储下载与本地缓存；
- 模型分发任务；
- 模型版本和校验值。

模型登记接口应保持“模型来源 + 容器可见路径”的抽象，避免绑定某一种存储。

### 8.3 推理服务能力

可逐步增加：

- readiness/liveness 探针；
- 服务网关和统一域名；
- 滚动升级；
- 手动或指标驱动扩缩容；
- 模型灰度和版本切换；
- 部署失败原因结构化展示。

### 8.4 数据库与审计

当前 H2 适合 MVP。需要多人长期运行时再引入：

- PostgreSQL 或 MySQL；
- Flyway/Liquibase 迁移；
- 操作审计；
- 配置版本和回滚；
- 更细的角色权限。

### 8.5 资源回收与对账

可增加周期性对账：

- 数据库部署与 Kubernetes 对象是否一致；
- Node 标签与资源池关系是否一致；
- HAMi 节点配置与共享规格是否一致；
- 配额使用量与实际副本是否一致。

这类能力应先提供检查和人工修复，再演进为自动修复。

## 9. 建议迭代顺序

1. 稳定真实 GPU、HAMi 和 DCGM 的标准接入。
2. 补齐推理服务 vLLM Metrics 和告警后端。
3. 完成负载感知的真实数据闭环。
4. 以 JSON 快照实现数字孪生 MVP。
5. 通过独立 Job 接入 SimAI。
6. 完成四种策略的 KPI 对比。
7. 最后评估自动扩缩容、故障处置和生产策略应用。

这一路线复用现有平台能力，同时让创新实验室保持可验证、可解释和可逐步落地。
