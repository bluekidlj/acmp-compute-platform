# 创新实验室 SimAI MVP 设计

## 1. 建设目标

创新实验室围绕一条可以演示、可以解释的闭环建设：

1. 负载感知分析银行大模型业务的历史负载；
2. 数字孪生固化负载、模型和算力资源快照；
3. 管理员向孪生环境注入负载或故障；
4. ACMP 将实验场景转换为 SimAI 输入并运行离线仿真；
5. 策略化运营对比多种资源策略的 KPI，形成运营建议。

MVP 只提供离线分析和仿真建议，不自动修改真实 Kubernetes 集群。

## 2. 功能边界

### 2.1 包含

- 银行业大模型负载画像；
- 真实监控、样本曲线、人工曲线三种负载来源；
- 资源、模型、负载静态快照；
- 负载注入；
- 故障注入；
- 平均分配、利用率优先、成本优先、SLA 优先四种策略；
- SimAI Analytical 离线仿真；
- 基线与实验策略 KPI 对比。

### 2.2 不包含

- 向真实集群注入故障；
- 自动执行推荐策略；
- 复杂机器学习负载分类；
- NS-3 细粒度网络仿真；
- 完整计费系统；
- 分布式实验编排和消息队列；
- 无依据的“AI 自动决策”。

## 3. 总体链路

```text
Prometheus / 样本曲线 / 人工曲线
                  |
                  v
          银行业负载感知
                  |
                  v
              负载画像
                  |
                  v
     模型快照 + 资源快照 + 负载快照
                  |
                  v
              数字孪生
            /           \
       负载注入       故障注入
            \           /
                  v
          ACMP SimAI Adapter
                  |
                  v
          SimAI Analytical
                  |
                  v
        多策略 KPI 对比与建议
```

SimAI 是性能仿真引擎，不负责采集监控数据，也不直接承担 Kubernetes 调度。

## 4. 银行业大模型负载感知

### 4.1 典型业务画像

MVP 预设以下银行业务类型。预设只定义分析模板，不制造监控数据。

| 业务类型 | 典型特征 | 重点指标 | 常见风险 |
|---|---|---|---|
| 智能客服 | 日间持续请求，午间或活动期间出现峰值，多轮对话 | QPS、并发、首 Token 延迟、P95 延迟、输出 Token | 排队增长、响应超时 |
| 员工知识助手 | 工作时间集中，早会和材料准备时段明显升高 | QPS、输入 Token、检索耗时、P95 延迟 | 长文档导致 Prefill 压力 |
| 智能营销助手 | 营销活动期间突发，平时负载较低 | 峰值 QPS、并发、成功率、扩容时间 | 短时容量不足 |
| 风控与反欺诈辅助 | 交易高峰相关，低延迟和高可用要求明显 | P99 延迟、SLA 达标率、失败率 | SLA 违约影响业务判断 |
| 合规审查与报告生成 | 大输入、长输出、任务持续时间长，批处理明显 | Token 数、任务耗时、显存、吞吐量 | 长请求挤占在线服务 |
| 票据与文档处理 | 营业结束后集中执行，批量任务特征明显 | 队列长度、批处理吞吐、完成时间 | 与在线推理争抢资源 |

### 4.2 负载数据

推理服务最小采集项：

- 请求 QPS；
- 并发请求数；
- 输入 Token 数；
- 输出 Token 数；
- 首 Token 延迟；
- P95、P99 响应时间；
- 请求成功数和失败数；
- 排队请求数；
- 副本数和就绪副本数；
- GPU 利用率和显存使用率。

监控序列必须能够通过以下标签关联到平台业务：

- `tenant_id`：租户；
- `project_id`：项目；
- `deployment_id`：推理服务；
- `namespace`：Kubernetes Namespace；
- `pod`：Pod；
- `node`：Node；
- `gpu_uuid`：GPU 设备。

### 4.3 负载模式

MVP 使用简单、可解释的统计规则识别：

| 模式 | 判定含义 |
|---|---|
| 稳定型 | 负载长期稳定，波动较小 |
| 周期型 | 每日或固定业务时段重复出现高峰 |
| 突发型 | 短时间内 QPS 或并发快速增长 |
| 批处理型 | 有明确开始、结束时间，期间持续占用资源 |
| 长上下文型 | 输入 Token 较大，Prefill 时间和显存压力明显 |
| 长输出型 | 输出 Token 较大，Decode 时间较长 |
| 低效占用型 | 已申请 GPU，但长期利用率较低 |
| 混合冲突型 | 在线低延迟业务与批处理任务同时争抢资源 |

一个业务可以同时具备多个模式，例如“周期型 + 长上下文型”。

### 4.4 数据真实性

页面必须显示数据来源：

- `PROMETHEUS`：真实监控；
- `SAMPLE`：演示样本；
- `MANUAL`：管理员人工录入。

Docker Desktop 模拟 GPU 没有真实 DCGM 性能数据，本地演示结果必须标记为“样本数据/估算结果”。

## 5. 数字孪生

### 5.1 孪生场景

每次实验固化三类快照：

1. 负载快照：时间曲线、请求量、Token 分布和 SLA；
2. 模型快照：模型名称、类型、存储路径和必要的模型参数；
3. 资源快照：节点、GPU 品牌、型号、显存、数量和分配规格。

实验创建后不随真实集群变化，保证基线和各策略使用相同输入。

### 5.2 实验时间轴

实验使用分钟作为 MVP 时间粒度。注入事件记录开始时间和持续时间，例如：

```text
00:00  开始重放基线负载
11:30  进入午间业务高峰
12:00  注入 3 倍请求流量
12:10  注入 GPU 0 下线
12:30  GPU 0 恢复
13:00  负载注入结束
24:00  仿真结束
```

当 SimAI 不能在一次运行中表达动态资源变化时，ACMP Adapter 按事件边界切分阶段，分别运行后合并结果。

## 6. 负载注入

MVP 支持三类负载事件：

### 6.1 流量突增

- 开始时间；
- 持续时间；
- QPS 倍率。

适用于营销活动、客服集中咨询和突发业务事件。

### 6.2 并发增长

- 开始时间；
- 持续时间；
- 目标并发数。

用于观察排队长度、响应时间和 SLA 达标率。

### 6.3 长请求注入

- 开始时间；
- 持续时间；
- 请求占比；
- 输入 Token 数；
- 输出 Token 数。

适用于知识库长文问答、合规材料审查和报告生成。

## 7. 故障注入

故障只改变数字孪生场景，不操作真实 Kubernetes 资源。

### 7.1 GPU 下线

- 开始时间；
- 持续时间；
- Node；
- GPU 编号。

实验期间目标 GPU 不可用，用于分析单卡故障对业务 SLA 的影响。

### 7.2 Node 下线

- 开始时间；
- 持续时间；
- Node。

实验期间 Node 及其全部 GPU 不可用。当前只有一台 GPU Worker 时，结果可能是推理容量归零，此结果符合真实资源约束。

### 7.3 网络带宽降级

- 开始时间；
- 持续时间；
- 剩余带宽比例。

ACMP Adapter 调整 SimAI 带宽参数。单机单卡场景影响可能不明显，主要用于未来多 GPU Worker 或多卡通信演示。

MVP 不模拟 ECC、CUDA XID、显存泄漏、磁盘和 API Server 等复杂故障。

## 8. 策略化运营

ACMP 将每个策略转换成一份资源与请求调度参数，再交给 SimAI。四种策略不是 SimAI 内置的 Kubernetes 调度策略。

| 策略 | MVP 行为 |
|---|---|
| 平均分配 | 请求和 GPU 在副本之间均匀分配 |
| 利用率优先 | 优先提高已有副本利用率，达到阈值后增加资源 |
| 成本优先 | 使用较少 GPU，允许在 SLA 范围内排队 |
| SLA 优先 | 预留冗余容量，在峰值前提供更多副本 |

所有策略运行相同的负载和故障事件，确保结果可比较。

## 9. KPI

MVP 只保留以下指标：

- P95 响应时间；
- 请求或 Token 吞吐量；
- SLA 达标率；
- GPU 平均利用率；
- GPU 使用卡时；
- 最大排队请求数；
- 故障恢复后的性能恢复时间。

结果页同时展示基线、注入后结果和各策略结果，不将估算值描述为真实生产结果。

## 10. SimAI 接入

第一版使用 SimAI Analytical，避免引入 NS-3 复杂网络仿真。

SimAI 以独立容器运行：

```text
harbor.internal/acmp/simai-runner:<version>
```

运行流程：

1. ACMP 创建实验并保存快照；
2. Adapter 根据策略和注入事件生成 workload 与配置；
3. 后端创建一次 Kubernetes Job；
4. `simai-runner` 执行离线仿真；
5. Runner 输出统一 `result.json`；
6. ACMP 保存结果摘要和原始日志位置；
7. 前端展示 KPI 对比。

ACMP Java 进程不直接编译或嵌入 SimAI。

## 12. 前端页面

创新实验室使用三个 Tab：

### 12.1 负载感知

- 选择银行业务类型和推理服务；
- 选择数据来源及时间范围；
- 查看 QPS、Token、延迟和 GPU 曲线；
- 查看负载模式和判定原因；
- 创建仿真实验。

### 12.2 数字孪生

- 展示负载、模型和资源快照；
- 在时间轴添加负载注入和故障注入；
- 选择参与对比的策略；
- 启动 SimAI 仿真；
- 查看运行状态和日志。

### 12.3 策略运营

- 对比基线和各策略 KPI；
- 展示负载、延迟、利用率随时间的变化；
- 展示推荐策略及可解释原因；
- 查看原始仿真结果；
- 不提供自动应用到真实集群的按钮。

## 13. MVP 演示故事

1. 管理员选择“智能客服”推理服务；
2. 负载感知识别出“工作日周期型 + 午间突发型”；
3. 创建包含当前模型和 GPU 资源的数字孪生；
4. 在 12:00 注入三倍流量；
5. 在 12:10 注入一张 GPU 下线，20 分钟后恢复；
6. SimAI 分别运行四种运营策略；
7. 页面对比 P95、SLA、吞吐量、利用率和卡时；
8. 平台给出策略建议和原因；
9. 建议仅供管理员决策，不改变真实集群。

## 14. 后续迭代

完成 MVP 后再考虑：

- 接入真实 Prometheus、DCGM 和 vLLM 指标；
- 使用真实压测校准 SimAI 参数；
- 接入不同 GPU 品牌的监控 Exporter；
- 增加多 GPU Worker 网络仿真；
- 增加训练任务负载；
- 在明确安全边界后，对接独立的真实集群故障演练工具。
