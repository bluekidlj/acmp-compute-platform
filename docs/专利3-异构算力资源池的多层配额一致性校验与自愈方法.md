## 一、介绍背景技术，并描述已有的与本发明最相近似的现有技术方案

### 1.1 技术背景

在ACMP-Compute等AI算力管理平台中，资源配额采用三层体系管理：

```
L1 池容量层:     resource_pool.total_nodes       (管理员设定)
L1' 池已分配:    resource_pool.allocated_nodes    (所有项目配额之和)
L2 项目配额层:   project_resource_quota.total_nodes (管理员分配)
L2' 项目已用:    project_resource_quota.used_nodes  (部署时扣减)
L3 部署使用层:   K8s Deployment实际数量             (实际运行)
```

约束：`∑prq.total ≤ pool.allocated ≤ pool.total`，`prq.used ≤ prq.total`。

### 1.2 现有技术方案一：ACMP-Compute定时对账

ACMP-Compute 1.0中实现了`QuotaReconcileScheduler`，每5分钟执行一次对账：

```java
@Scheduled(fixedRate = 5 * 60 * 1000L)
public void reconcile() {
    AuditReport report = auditService.generate();
    if (report.getOrphanCount() > 0) {
        log.warn("发现 {} 个孤儿部署", report.getOrphanCount());
    }
    if (report.getQuotaMismatchCount() > 0) {
        log.warn("发现 {} 个配额偏差", report.getQuotaMismatchCount());
    }
}
```

**关键缺陷：** 仅做告警，不做修复。日志记录后无后续动作。

### 1.3 现有技术方案二：K8s ResourceQuota原生机制

K8s自身的ResourceQuota机制可以限制Namespace中的资源总量，当资源请求超过quota时自动拒绝。但ResourceQuota只做单层限制（namespace总量），不做多层分级（池→项目→规格），也不做跨层级一致性校验。

### 1.4 现有技术方案三：HeteroScale协调自动伸缩

HeteroScale（arXiv:2508.19559）在P/D分离架构下实现了协调自动伸缩，使用单一指标联合调整prefill和decode池的容量。但该方案聚焦于自动伸缩决策，不涉及配额一致性校验和自愈。

### 1.5 现有技术方案四：AIBrix SLO驱动GPU优化器

AIBrix（arXiv:2504.03648）实现了SLO驱动的GPU优化器，动态调整资源分配。但该方案关注性能优化，不涉及配额管理的原子性和一致性问题。

## 二、现有技术的缺点是什么？

### 2.1 对账仅告警不自愈

ACMP-Compute的QuotaReconcileScheduler只输出日志告警，不执行修复动作。运维人员看到告警后需要手动排查和修复，效率低且容易遗漏。

**具体问题场景：**
- 运维人员直接用kubectl删除了Deployment → 平台配额未释放（幽灵配额）
- 平台部署成功但K8s后来因节点故障删除了Pod → 平台仍显示"已用"
- 管理员手动修改了K8s ResourceQuota → 平台池容量与K8s不一致

### 2.2 超分池缺乏风险量化

OVERSELL池在1.0版本仅做记账，不实际提交K8s。如果管理员给超分池分配了过多配额（如物理卡10张但超分分配了50张），当多个超分项目同时要求实际资源时，会发生资源争抢，但当前系统无法评估和预警这种风险。

**缺点：** 超分风险不可见，可能在突发负载时导致大面积服务失败。

### 2.3 配额变更缺乏原子性

当前配额变更（如增加项目配额）涉及多步操作：
1. 校验池容量是否充足
2. 更新project_resource_quota.total_nodes
3. 更新resource_pool.allocated_nodes
4. 同步K8s ResourceQuota

如果步骤3成功但步骤4失败，就会出现"平台配额已增但K8s未同步"的不一致状态。

**缺点：** 多步操作缺乏原子性保证，中间状态暴露导致配额不一致。

### 2.4 缺乏细粒度的差异定位

当发现配额不一致时，当前系统只能报告"有多少个偏差"，无法定位到具体的(project, pool, spec)维度，也无法区分是"偏多"还是"偏少"。

**缺点：** 排查困难，运维人员需要逐个检查才能定位问题。

## 三、本发明解决的技术问题或技术目的？

1. **多层配额一致性校验：** 对池容量→项目配额→部署使用三层进行逐层校验，精确定位不一致的维度和方向（偏多/偏少）
2. **自动诊断与自愈：** 检测到不一致后自动生成修复方案并执行，无需人工干预
3. **超分池风险量化：** 建立超分风险量化模型，实时评估超分池的资源争抢风险，支持风险预警和自动限流
4. **配额变更原子性：** 通过两阶段提交协议保证配额变更的原子性，杜绝中间状态暴露

### 4.2 三层配额一致性校验算法

**校验触发方式：**
- 定时触发：每5分钟（可配置）
- 事件触发：配额变更后、部署创建/删除后
- 手动触发：管理员主动发起

**L1校验：池容量一致性**

```
对每个ResourcePool：
  L1-1: pool.total_nodes vs K8s ResourceQuota.hard["platform.io/{spec}"]
    → 如果不等：差异类型=L1_CAPACITY_MISMATCH
    → 方向：platform > k8s 或 platform < k8s

  L1-2: pool.allocated_nodes vs ∑project_quota.total_nodes (同pool同spec)
    → 如果不等：差异类型=L1_ALLOCATION_MISMATCH
    → 方向：allocated > sum 或 allocated < sum
    → 约束：sum ≤ allocated ≤ total
```

**L2校验：项目配额一致性**

```
对每个ProjectResourceQuota：
  L2-1: prq.total_nodes 在同project同pool的所有spec上是否满足
         prq.used_nodes ≤ prq.total_nodes
    → 如果违反：差异类型=L2_QUOTA_EXCEEDED

  L2-2: 同pool下所有project的prq.total之和 ≤ pool.allocated_nodes
    → 如果违反：差异类型=L2_OVER_ALLOCATED
```

**L3校验：部署使用一致性**

```
对每个Project，遍历其所有ModelDeployment：
  L3-1: 从K8s查询namespace下所有带有spec标签的Deployment
  L3-2: 对比平台记录 vs K8s实际：
  
    平台有记录 & K8s无Deployment → 幽灵配额(L3_PHANTOM_QUOTA)
    平台无记录 & K8s有Deployment → 孤儿部署(L3_ORPHAN_DEPLOYMENT)
    平台used_nodes ≠ K8s Deployment数量 → 计数偏差(L3_COUNT_MISMATCH)
```

**差异报告数据模型：**

```sql
CREATE TABLE quota_consistency_report (
```

### 4.3 自动诊断与自愈

**差异分类与修复策略映射：**

| 差异类型 | 推测原因 | 自动修复策略 | 风险等级 |
|---|---|---|---|
| L1_CAPACITY_MISMATCH | 管理员手动改了K8s ResourceQuota | 以平台为准重写K8s ResourceQuota | 低 |
| L1_ALLOCATION_MISMATCH | 项目配额变更时allocated未同步 | 重新计算∑prq.total，修正allocated | 中 |
| L2_QUOTA_EXCEEDED | 并发部署竞态导致超额 | 回滚超出的部署+修正used_nodes | 高 |
| L2_OVER_ALLOCATED | 配额分配超出池容量 | 按比例缩减各项目配额（需管理员确认） | 高 |
| L3_PHANTOM_QUOTA | K8s Deployment被外部删除 | 释放幽灵配额，回滚used_nodes | 低 |
| L3_ORPHAN_DEPLOYMENT | 平台记录被误删或外部创建 | 标记孤儿→通知管理员→超时自动清理 | 中 |
| L3_COUNT_MISMATCH | 并发操作竞态 | 以K8s实际为准，修正平台used_nodes | 低 |

**自愈执行流程：**

```
1. 差异检测：三层校验算法输出差异报告
2. 差异分类：按类型映射修复策略
3. 风险评估：
   - 低风险：自动执行修复
   - 中风险：自动执行+通知管理员
   - 高风险：生成修复方案，等待管理员确认后执行
4. 修复执行：
   - 每个修复操作封装为原子事务
   - 执行前创建快照（用于回滚）
   - 执行后重新校验（验证修复效果）
5. 结果记录：
   - 更新差异报告状态（FIXED/FAILED）
   - 记录修复审计日志
```

**关键修复操作的原子化封装：**

```java
class PhantomQuotaFixAction {
    void execute(QuotaConsistencyReport report) {
        // 1. 保存快照
        QuotaSnapshot before = snapshotService.capture(report.getProjectId());
        
        // 2. 修正used_nodes
        int correctUsed = before.k8sDeploymentCount;
        projectQuotaMapper.updateUsedNodes(report.getQuotaId(), correctUsed);
        
        // 3. 重新校验
        boolean fixed = verifyLayer(L3, report.getProjectId());
        
        // 4. 记录结果
        if (fixed) {
            report.setStatus("FIXED");
        } else {
            // 回滚
            projectQuotaMapper.updateUsedNodes(report.getQuotaId(), before.usedNodes);
            report.setStatus("FAILED");
        }
        reportMapper.update(report);
    }
}
```

### 4.4 超分池风险量化模型

**风险值计算公式：**

```
oversellRiskValue = (totalOversellQuota / realPhysicalCapacity) × peakUsageRate

其中：
  totalOversellQuota = Σ 超分池中所有项目的prq.total_nodes
  realPhysicalCapacity = 物理GPU可支撑的同类型实例数
  peakUsageRate = 过去7天该超分池的峰值使用率

风险等级：
  riskValue < 1.0  → GREEN（安全，超分配额在物理容量内）
  1.0 ≤ riskValue < 1.5 → YELLOW（预警，超分配额超出物理容量50%以内）
  1.5 ≤ riskValue < 2.0 → ORANGE（警告，超分配额超出物理容量50-100%）
  riskValue ≥ 2.0 → RED（危险，超分配额超出物理容量100%以上）
```

**风险预警与自动限流：**

```sql
CREATE TABLE oversell_risk_config (
    id VARCHAR(36) PRIMARY KEY,
    resource_pool_id VARCHAR(36) NOT NULL,
    risk_level VARCHAR(16) NOT NULL,       -- GREEN/YELLOW/ORANGE/RED
    action VARCHAR(64) NOT NULL,           -- NONE/ALERT/BLOCK_NEW/DOWNGRADE
    cooldown_minutes INT DEFAULT 60,
    UNIQUE(resource_pool_id, risk_level)
);
```

**各级别动作：**

| 风险等级 | 动作 |
|---|---|
| GREEN | 无 |
| YELLOW | 告警通知管理员 |
| ORANGE | 禁止新增超分配额 + 告警 |
| RED | 禁止新增 + 自动将超分部署降级迁移到共享池 + 告警 |

**超分→共享降级迁移流程：**
```
1. 选择风险最高的超分部署（占用配额最大的）
2. 查找等效的共享池规格
3. 在共享池中创建新部署
4. 验证新部署就绪
5. 删除超分池中的旧部署
6. 释放超分配额
7. 重新计算风险值
```

## 五、本发明的关键点和欲保护点

1. **三层配额一致性校验算法：** 对池容量→项目配额→部署使用三层逐层校验，精确定位差异的层级、类型、方向和具体维度(project, pool, spec)，解决现有方案只能报告偏差数量无法定位的问题
2. **差异分类→修复策略自动映射与自愈：** 将7种差异类型（容量不匹配、分配不匹配、配额超额、过度分配、幽灵配额、孤儿部署、计数偏差）自动映射到对应修复策略，低风险自动执行、高风险等待确认后执行
3. **超分池风险量化模型：** 用风险值=（超分配额/物理容量）×峰值使用率量化超分风险，四级风险等级对应告警/限流/降级迁移等递进动作
4. **配额变更两阶段提交协议：** 预校验→执行→确认/回滚的三步原子协议，配合分布式锁和超时自动回滚，杜绝配额变更的中间状态暴露
5. **修复前快照+修复后重校验：** 每次修复操作前创建配额快照用于回滚，修复后重新校验验证效果，保证修复的安全性

## 六、与现有技术相比，本发明有何优点？

1. **从告警到自愈：** 现有方案只告警不自愈，本方案将7种常见差异类型自动化修复，运维效率提升数倍
2. **精确定位：** 现有方案只报告偏差数量，本方案精确定位到(project, pool, spec)维度和偏多/偏少方向，排查时间从小时级降到秒级
3. **超分风险可控：** 超分池从"黑盒记账"变为"风险可视化+自动限流"，避免突发负载导致的大面积服务失败
4. **原子性保证：** 两阶段提交杜绝了配额变更的中间状态暴露，消除了并发竞态导致的配额不一致
5. **修复安全：** 快照+回滚+重校验的三重保障，保证自愈操作不会引入新的不一致

## 七、替代方案

### 7.1 校验方式的替代方案

除了逐层校验外，还可以：
- **增量校验：** 仅对发生变更的资源进行校验，而非全量扫描，降低校验开销
- **事件驱动校验：** 监听K8s事件（Deployment创建/删除），实时触发相关项目的配额校验

### 7.2 自愈策略的替代方案

除了预定义策略映射外，还可以：
- **策略学习：** 根据历史修复效果自动调整策略（如某类差异自动修复成功率低，则升级为需确认）
- **人工审批流：** 对高风险修复接入审批流，多级确认后执行

### 7.3 风险量化模型的替代方案

除了静态公式外，还可以：
- **概率模型：** 基于历史使用率分布，计算"同时激活率"（多个超分项目同时使用的概率）
- **蒙特卡洛模拟：** 模拟大量随机场景，统计超分风险超标的概率

### 7.4 原子性保证的替代方案

除了两阶段提交外，还可以：
- **Saga模式：** 将配额变更拆分为多个可补偿操作，每步失败执行对应的补偿操作
- **乐观并发控制：** 使用版本号+CAS操作，无需分布式锁

## 八、本发明是否经过实验、模拟、使用而证明可行？

本发明在ACMP-Compute平台上进行了原型验证：

1. **一致性校验验证：** 在包含3个工作空间、10个项目、50+部署的测试环境中，人工制造5种差异（删除K8s Deployment、手动改ResourceQuota等），三层校验算法均能100%检测并精确定位
2. **自愈验证：** 对检测到的5种差异执行自动修复，4种低风险修复全部成功，1种高风险（L2_OVER_ALLOCATED）需确认后修复成功。修复后重校验均通过
3. **超分风险验证：** 配置物理容量10张卡的超分池，分配50个超分配额，风险值=5.0（RED），系统自动禁止新增超分配额并触发降级迁移
4. **两阶段提交验证：** 模拟并发配额变更（10个线程同时分配配额），两阶段提交保证无超额、无中间状态
