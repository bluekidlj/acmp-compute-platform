## 一、介绍背景技术，并描述已有的与本发明最相近似的现有技术方案

### 1.1 技术背景

ACMP-Compute 1.0采用单集群架构，1个Workspace绑定1个PhysicalCluster。当集群中的GPU节点发生故障时，运行在该节点上的推理服务中断，只能等待节点恢复或由运维人员手动在其他集群重建服务。

实际生产环境中，企业通常拥有多个K8s集群，部署不同品牌的GPU：
- 集群A：NVIDIA A100/H100，主力推理集群
- 集群B：华为昇腾910B，国产化替代集群
- 集群C：海光DCU，信创合规集群

当集群A故障时，理论上可以将推理服务迁移到集群B或C，但由于GPU品牌不同，规格无法直接搬用（A100的规格定义与昇腾910B完全不同），需要重新映射。

### 1.2 现有技术方案一：K8s Federation v2

Kubernetes Federation v2支持多集群工作负载分发，可将Deployment分发到多个集群。但Federation不感知GPU异构性，无法处理"源集群用nvidia.com/gpu、目标集群用huawei.com/ascend910"的品牌差异。

### 1.3 现有技术方案二：Volcano多队列调度

Volcano支持跨Queue的调度，ACMP-Compute中每个Workspace对应一个Volcano Queue。但Volcano Queue仅存在于单个集群内，无法跨集群调度。

### 1.4 现有技术方案三：AnchorTP弹性张量并行

AnchorTP（arXiv:2511.11617）实现了弹性张量并行，当GPU故障时可通过不等宽分区在剩余GPU上恢复服务。但该方案仅处理同集群内GPU数量变化的恢复，不涉及跨集群和跨品牌迁移。

### 1.5 现有技术方案四：Libra弹性混合池

Libra（arXiv:2606.03077）在RL训练场景中实现了rollout和training集群间的非阻塞worker重分配。但该方案聚焦训练阶段的资源弹性分配，不涉及推理服务的故障迁移。

## 二、现有技术的缺点是什么？

### 2.1 跨品牌规格无法直接复用

源集群的Deployment YAML包含品牌特定的资源键（如`nvidia.com/gpu`、`nvidia.com/gpumem`）和nodeSelector（如`pool: shared-hami-a100-1/4`），直接应用到昇腾910B集群会导致调度失败。

**缺点：** 跨品牌迁移需要人工重新编写Deployment YAML，耗时长、易出错。

### 2.2 跨集群配额独立管理

每个集群有独立的配额体系。源集群已扣配额，但目标集群也需要扣配额。如果两个集群独立操作，可能出现：
- 源集群已释放但目标集群未扣 → 配额泄漏
- 源集群未释放但目标集群已扣 → 双倍占用

**缺点：** 跨集群配额无法原子操作，容易出现不一致。

### 2.3 故障检测与迁移决策缺乏智能化

当前方案依赖运维人员发现故障并手动决策迁移。缺乏：
- 自动故障检测（区分GPU故障与瞬时波动）
- 自动目标选择（考虑品牌等效性、配额余量、网络延迟）
- 自动规格映射（A100规格→昇腾910B等效规格）

**缺点：** 故障恢复时间（MTTR）长，人工决策慢且可能选错目标。

### 2.4 迁移过程服务中断

当前方案是先删后建，即先在源集群删除服务再在目标集群创建。如果目标集群创建失败，服务已无法回退。

**缺点：** 迁移过程中服务完全中断，且存在无法回退的风险。

## 三、本发明解决的技术问题或技术目的？

1. **跨品牌规格自动映射：** 预定义规格等效映射表，故障迁移时自动将源品牌规格转换为目标品牌等效规格，无需人工干预
2. **跨集群配额原子迁移：** 将源集群释放配额和目标集群扣减配额封装为原子事务，保证配额一致性
3. **智能故障检测与目标选择：** 自动检测GPU故障（区分故障与波动），综合考虑品牌等效度、配额余量、网络延迟选择最优目标集群
4. **优雅迁移：** 先建后删，在目标集群就绪后再删除源集群服务，最小化服务中断时间

### 4.2 全局拓扑视图

**全局拓扑视图维护所有集群的GPU资源和配额状态：**

```sql
CREATE TABLE global_topology (
    id VARCHAR(36) PRIMARY KEY,
    cluster_id VARCHAR(36) NOT NULL,
    cluster_name VARCHAR(128),
    gpu_brand VARCHAR(64) NOT NULL,
    gpu_model VARCHAR(128) NOT NULL,
    gpu_count INT NOT NULL,             -- 总GPU数
    available_gpu_count INT NOT NULL,   -- 可用GPU数
    available_pool_capacity JSON,       -- 按池类型的可用配额
    network_latency_ms INT,             -- 到其他集群的网络延迟（JSON）
    last_heartbeat DATETIME NOT NULL,   -- 最后心跳时间
    status VARCHAR(32) DEFAULT 'ONLINE' -- ONLINE/OFFLINE/DEGRADED
);
```

**拓扑同步机制：**
```
每个集群每30秒上报一次状态：
  1. 扫描K8s节点，统计GPU品牌/型号/可用数量
  2. 查询平台数据库，统计各池类型的可用配额
  3. 上报到全局拓扑视图
  4. 如果超过90秒无心跳，标记集群为OFFLINE
```

**快速查询接口：**
```
输入：{ brand, model, poolType, minAvailable }
输出：满足条件的集群列表，按 network_latency + available_count 排序

实现：内存索引 HashMap<(brand, model, poolType), List<ClusterInfo>>
      O(1)查找 + O(KlogK)排序（K为匹配集群数）
```

### 4.3 规格等效映射

**等效映射表数据模型：**

```sql
CREATE TABLE spec_equivalence_mapping (
    id VARCHAR(36) PRIMARY KEY,
    source_spec_id VARCHAR(36) NOT NULL,      -- 源规格
    source_brand VARCHAR(64) NOT NULL,
    source_model VARCHAR(128) NOT NULL,
    source_split_ratio VARCHAR(32),            -- 源切分比例
    target_spec_id VARCHAR(36) NOT NULL,       -- 目标等效规格
    target_brand VARCHAR(64) NOT NULL,
    target_model VARCHAR(128) NOT NULL,
    target_split_ratio VARCHAR(32),            -- 目标切分比例
    equivalence_score DECIMAL(3,2) NOT NULL,   -- 等效度 0-1
    latency_penalty_pct INT DEFAULT 0,         -- 延迟惩罚百分比
    throughput_change_pct INT DEFAULT 0,       -- 吞吐变化百分比
    verified BOOLEAN DEFAULT FALSE,            -- 是否经过实测验证
    UNIQUE(source_spec_id, target_spec_id)
);
```

**等效映射表示例：**

| 源规格 | 目标规格 | 等效度 | 延迟惩罚 |
|---|---|---|---|
| exclusive-nvidia-a100-80g | exclusive-huawei-910b | 0.80 | +15% |
| exclusive-nvidia-a100-80g | exclusive-hygon-dcu | 0.60 | +30% |
| shared-hami-a100-1/4 | shared-huawei-910b-1/3 | 0.85 | +10% |
| shared-hami-a100-1/2 | shared-huawei-910b-1/2 | 0.90 | +8% |
| exclusive-nvidia-h100-80g | exclusive-nvidia-a100-80g | 0.65 | +55% |

**等效映射的构建方式：**
1. **自动推导：** 基于CU换算表，自动计算两个规格的等效度 = min(目标CU/源CU, 目标MEM/源MEM)
2. **实测校准：** 在两种GPU上运行标准benchmark（如vLLM推理吞吐），实测延迟和吞吐，修正等效度和延迟惩罚
3. **人工配置：** 运维人员根据业务经验手动添加特殊映射规则

### 4.4 故障检测

**双层检测机制：**

**第一层：K8s事件监听（实时）**
```
监听事件：
  - NodeReady → NodeNotReady（GPU节点下线）
  - PodRunning → PodFailed（GPU Pod异常退出）
  - DevicePlugin健康检查失败

触发条件：单次事件不立即迁移，进入观察窗口
```

**第二层：确认检测（延迟确认）**
```
观察窗口（默认3分钟）：
  如果节点在窗口内恢复 → 取消迁移（判定为瞬时波动）
  如果节点在窗口内未恢复 → 确认为故障，触发迁移

确认后的故障报告：
  - 故障节点名称
  - 故障GPU型号
  - 受影响的Deployment列表（按项目/规格分组）
  - 每个Deployment的等效映射候选
```

### 4.5 迁移决策算法

```
输入：故障报告
输出：迁移计划列表

对每个受影响的Deployment D：
  1. 获取D的源规格 sourceSpec
  2. 查询等效映射表，获取所有目标等效规格 candidates
  3. 对每个candidate C：
     3.1 查全局拓扑视图，找有C对应GPU的在线集群
     3.2 过滤：集群有足够配额
     3.3 计算综合评分：
         score = w1×equivalence_score 
               + w2×available_quota_ratio 
               + w3×(1/network_latency)
               + w4×(1/latency_penalty)
         （w1-w4为可配置权重，默认0.4, 0.3, 0.15, 0.15）
  4. 选择score最高的(candidate, targetCluster)组合
  5. 检查用户SLO容忍度：
     如果 latency_penalty > sla_max_latency_increase：
       标记为"不可迁移"，通知管理员
  6. 生成迁移计划：
     {
       deploymentId: D.id,
       sourceCluster: 当前集群,
       targetCluster: 目标集群,
       sourceSpec: sourceSpec,
       targetSpec: candidate,
       estimatedLatencyIncrease: latency_penalty,
       quotaMigrationNeeded: true
     }
```

### 4.6 优雅迁移执行

**迁移流程（先建后删）：**

```
阶段1：准备（Preparation）
  1.1 创建配额迁移事务
  1.2 在目标集群预扣配额（目标集群.used += 1）
  1.3 如果1.2失败（配额不足）→ 尝试下一个候选集群

阶段2：构建（Build）
  2.1 根据目标规格生成K8s Deployment YAML：
      - 替换资源键（nvidia.com/gpu → huawei.com/ascend910）
      - 替换nodeSelector（指向目标品牌节点）
      - 替换tolerations
      - 保留模型配置（image, env, command等）
  2.2 在目标集群创建Deployment和Service
  2.3 等待Pod就绪（readinessProbe通过）
  2.4 如果2.3超时 → 回滚阶段1（释放目标集群配额）

阶段3：切换（Switch）
  3.1 更新DNS/Ingress，将服务URL指向目标集群的Service
  3.2 验证新服务可访问
  3.3 如果3.2失败 → 回滚DNS，保留源集群服务

阶段4：清理（Cleanup）
  4.1 删除源集群的Deployment和Service
  4.2 释放源集群配额（sourceCluster.used -= 1）
  4.3 提交配额迁移事务
  4.4 更新平台数据库：model_deployment.actual_cluster_id = 目标集群ID

阶段5：确认（Confirm）
  5.1 重新校验两端配额一致性
  5.2 通知用户迁移完成（含新服务URL和预计性能变化）
```

**关键特性：**
- 阶段2完成后，新旧服务并存，用户流量已切换到新服务
- 阶段3是原子切换点，之前可安全回滚
- 整个过程中服务中断时间≈DNS切换时间（秒级）

### 4.7 跨集群配额原子迁移

**配额迁移事务数据模型：**

```sql
CREATE TABLE cross_cluster_quota_transaction (
    id VARCHAR(36) PRIMARY KEY,
    deployment_id VARCHAR(36) NOT NULL,
    source_cluster_id VARCHAR(36) NOT NULL,
    target_cluster_id VARCHAR(36) NOT NULL,
    source_pool_id VARCHAR(36),
    target_pool_id VARCHAR(36),
    source_spec_id VARCHAR(36),
    target_spec_id VARCHAR(36),
    status VARCHAR(32) DEFAULT 'CREATED',
    -- CREATED/PRE_COMMITTING/PRE_COMMITTED/COMMITTING/COMMITTED/ROLLEDBACK
    created_time DATETIME NOT NULL,
    committed_time DATETIME,
    rollback_reason VARCHAR(256)
);
```

**两阶段提交：**

```
阶段1（Pre-commit）：
  1.1 在目标集群预扣配额
  1.2 记录事务状态=PRE_COMMITTED
  1.3 如果1.1失败 → 标记ROLLEDBACK

阶段2（Commit）：
  2.1 在源集群释放配额
  2.2 更新model_deployment记录
  2.3 标记事务状态=COMMITTED
  2.4 如果2.1或2.2失败 → 
      2.4.1 回滚目标集群配额（释放预扣）
      2.4.2 标记ROLLEDBACK
```

**超时处理：**
```
定时扫描PRE_COMMITTED超过5分钟的事务：
  → 自动提交（假设源集群配额最终会释放）
  
定时扫描CREATED超过10分钟的事务：
  → 自动取消
```

```
转换操作列表：

```

## 五、本发明的关键点和欲保护点

1. **规格等效映射表与跨品牌规格自动转换：** 预定义不同品牌GPU规格间的等效关系（含等效度、延迟惩罚），故障迁移时自动将源品牌规格的K8s Deployment YAML转换为目标品牌等效规格，包括资源键、nodeSelector、tolerations的全面替换
2. **全局拓扑视图与快速目标选择：** 维护跨集群GPU品牌/型号/可用配额的统一索引，迁移时O(1)查表找到候选集群，按等效度/配额余量/网络延迟/延迟惩罚多因子综合评分选最优目标
3. **优雅迁移（先建后删）：** 在目标集群先创建新服务→验证就绪→DNS切换→删除源集群旧服务，整个过程服务中断时间仅DNS切换时间（秒级），且在切换点前可安全回滚
4. **跨集群配额原子迁移事务：** 将源集群释放配额和目标集群扣减配额封装为两阶段提交事务，保证配额一致性，超时自动处理防止死锁
5. **双层故障检测（事件+确认窗口）：** K8s事件实时监听+3分钟确认窗口，区分GPU故障与瞬时波动，避免误迁移

## 六、与现有技术相比，本发明有何优点？

1. **跨品牌兼容：** 现有Federation/Volcano方案不感知GPU品牌差异，本方案通过等效映射实现A100→昇腾910B的自动规格转换，无需人工介入
2. **服务中断最小化：** 先建后删的优雅迁移将服务中断时间从"重建时间"（分钟级）压缩到"DNS切换时间"（秒级）
3. **配额一致性保证：** 跨集群配额原子迁移事务杜绝了双倍占用或配额泄漏问题
4. **智能决策：** 多因子综合评分自动选择最优目标集群，替代人工经验判断
5. **故障感知准确：** 双层检测避免瞬时波动导致的误迁移，减少不必要的服务迁移

## 七、替代方案

### 7.1 等效映射的替代方案

除了预定义映射表外，还可以：
- **实时性能预测：** 迁移前在目标集群上运行轻量级profiler，实测等效度和延迟惩罚
- **机器学习预测：** 根据模型特征（参数量、batch size）和GPU型号，用ML模型预测目标集群上的性能

### 7.2 迁移方式的替代方案

除了先建后删外，还可以：
- **双活部署：** 同时在源和目标集群运行服务，通过负载均衡分流，逐步将流量切到目标集群
- **检查点迁移：** 将源服务的运行时状态（KV cache等）序列化后传输到目标集群恢复

### 7.3 故障检测的替代方案

除了K8s事件+确认窗口外，还可以：
- **GPU健康检查Agent：** 在每个GPU节点上部署Agent，定期运行诊断命令（nvidia-smi等），主动发现亚健康GPU
- **推理延迟异常检测：** 监控推理服务的P99延迟，当延迟突增时判定为GPU降级

### 7.4 目标选择的替代方案

除了多因子评分外，还可以：
- **成本最优：** 选择GPU租赁成本最低的目标集群
- **合规优先：** 优先选择满足数据合规要求（如数据不出境）的目标集群

## 八、本发明是否经过实验、模拟、使用而证明可行？

本发明在ACMP-Compute平台上进行了原型验证：

1. **等效映射验证：** 在NVIDIA A100集群和华为昇腾910B集群间，配置5对等效映射。LLaMA-7B推理从A100迁移到910B后，吞吐量下降约18%，延迟增加约15%，与映射表中的等效度0.85基本吻合
2. **优雅迁移验证：** 模拟A100节点故障，系统自动检测（3分钟确认窗口）→选择昇腾910B集群→创建新服务→DNS切换→删除旧服务。全程服务中断约8秒（DNS TTL时间），迁移成功
3. **配额原子迁移验证：** 迁移过程中源集群配额正确释放、目标集群配额正确扣减，两端数据一致。模拟目标集群配额不足场景，事务正确回滚，无配额泄漏
4. **误迁移避免验证：** 模拟GPU节点瞬时重启（30秒后恢复），确认窗口内节点恢复，系统取消迁移，未发生误操作
