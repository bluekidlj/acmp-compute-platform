# 专利6、7 思路详细阐述

> 基于银行算力集群现状，从工单审批优化和Token合规两个维度补充的专利方向

---

## 专利6：基于SLA驱动的算力资源智能审批与动态规划方法

### 问题是什么

银行内部通过工单制申请算力资源，华为MA平台提供仿真功能预估资源量，管理员审批后部署服务。这个流程有三个层面的问题。

**第一个问题：业务方按"资源量"申请，而不是按"业务需求"申请。** 当前工单上填写的是"我需要2张A100"，而不是"我的智能客服P99延迟不能超过500ms"。但业务方其实并不知道自己需要几张A100——他们只知道业务指标（响应速度、并发量、可用性）。让业务方自己估算GPU资源量，往往有两种倾向：要么往高了报（反正审批过了就占着，不用白不用），要么估算不足（上线后服务卡顿再紧急扩容）。这两种情况都会导致算力资源分配不合理。

**第二个问题：审批人缺乏决策依据。** 审批人面对一个工单，能参考的信息只有工单描述和仿真结果。但他不知道：这个部门上一个工单申请了2张A100但实际只用了15%的效能；同类场景在其他部门的实际消耗只有仿真预估的30%；当前集群如果把这个工单批了，剩余容量还能支撑几个待审批工单。审批人只能凭经验判断，要么过于保守导致审批缓慢业务方等不起，要么过于激进导致集群过载已部署服务的SLA受损。

**第三个问题：已部署服务的SLA缺乏动态保障。** 工单审批的是静态资源量（比如2张A100），但GPU负载是波动的。闲时2张A100绰绰有余，高峰时可能扛不住，SLA下降。反过来，夜间几乎没有流量的时候，2张A100还在空转浪费。当前没有机制能根据实时负载动态调整资源，在保障SLA的前提下节省成本。

### 怎么解决

**第一步：从"按资源申请"转变为"按SLA申请"。** 工单模板改造，业务方不再填写GPU数量，而是填写SLA指标：

- 延迟类指标：P50/P90/P99延迟上限（如"P99 < 500ms"）
- 吞吐类指标：每秒请求数QPS（如"峰值200 QPS"）
- 可用性指标：月度可用率（如"99.9%"）
- 业务特征：请求模式（短对话/长文档/批处理）、高峰时段

系统根据这些SLA指标，结合模型网关的历史Token效能数据，自动计算保障该SLA所需的最小资源量。这个过程对业务方完全透明——他们只需要关心业务指标。

**第二步：用历史TEE基线校准仿真预估。** 华为MA的仿真给出一个初始资源预估值，但这个估值往往有偏差。系统自动查询同类场景（相同或相似场景标签）的历史Token效能画像——比如"智能客服"场景的历史数据显示，200 QPS的负载只需要0.3张A100的TEE效能，但仿真可能给了2张A100。系统用校准系数修正仿真结果，给出更接近实际的资源建议。校准公式：校准后资源 = 仿真资源 × 同类场景实际效能/仿真效能（取近30天数据的加权中位数，避免极端值影响）。

**第三步：全局容量校验，判断集群能否承受。** 系统汇总三部分数据：
- 已部署服务的SLA承诺 + 实际负载基线（从网关Token统计得到）
- 待审批工单的SLA需求 + 校准后的资源增量
- 集群各时段的Token吞吐上限（从GPU型号和数量计算，分闲时/平峰/高峰三档）

三者对比后，按时段给出容量规划建议。比如"工作日9-18点高峰时段容量不足，需排队等待或扩容；18-24点平峰时段可批准；0-8点闲时容量充足"。如果多个工单竞争同一时段的资源，按SLA优先级排序——合规审查类SLA优先于内部工具类。

**第四步：SLA驱动的动态资源调整。** 部署后不是一劳永逸的，系统持续监控服务的实际SLA达成情况：
- SLA持续达标且负载远低于资源分配 → 建议缩容（释放资源给其他服务）
- SLA接近临界值且负载上升趋势 → 预判性扩容（在SLA突破前增加资源）
- SLA已突破 → 紧急扩容（从共享池或超分池借用资源）

扩缩容操作和专利2的弹性切分机制联动——通过调整vGPU的切分比例来增减资源，而非重建服务。缩容省下来的资源自动回流到全局容量池，供新工单使用。

**第五步：审批智能辅助，给审批人明确的决策建议。** 系统为每个工单生成一份审批摘要：

```
工单：XX部门-智能客服扩容
SLA需求：P99<500ms，峰值200 QPS
仿真资源：2张A100
校准建议：0.8张A100（同类场景实际效能仅为仿真的40%）
容量校验：工作日高峰时段容量紧张，建议分批（先批0.5张，观察一周后决定是否追加）
风险提示：该部门历史工单使用率仅25%，建议设置资源回收策略
同类参考：信用卡部门同类场景实际使用0.3张A100，SLA达标
```

审批人可以一键采纳建议，也可以手动调整。每次审批决策和实际效果都会反馈到系统，持续优化校准模型。

### 核心创新点

1. **SLA驱动的资源申请模式** — 业务方声明SLA需求而非GPU数量，系统自动计算最小资源量
2. **仿真校准闭环** — 用同类场景历史TEE基线修正仿真偏差，持续优化预估准确性
3. **分时段全局容量规划** — 按闲时/平峰/高峰分档评估容量，支持时段级审批决策
4. **SLA驱动的动态资源调整** — 部署后持续监控SLA达成情况，预判性扩缩容
5. **审批智能辅助** — 基于历史数据和全局容量给出明确审批建议，非黑盒决策

### 与专利5的关系

专利5解决了"效能怎么量、容量怎么算"的问题（TEE效能画像 + 全局Token容量规划），是度量层。
本专利解决了"量出来之后怎么用于审批决策"的问题（SLA驱动 + 仿真校准 + 审批辅助），是决策层。
两者形成上下游关系：专利5提供数据基础，本专利提供决策逻辑。

## 专利7：LLM推理链路中Token流的敏感信息识别与脱敏方法

### 问题是什么

银行内部通过模型网关调用大模型推理服务，网关可以采集到每次调用的input_tokens和output_tokens。这些Token数据在多个环节被使用：

- Token统计：用于算力效能分析（专利5的TEE画像）
- 审计日志：用于合规审计，记录谁在什么时候调用了什么模型
- 成本分账：按Token消耗量分摊算力成本到各部门
- 异常检测：检测Token消耗的异常模式（可能的安全事件）

但问题是：推理请求中经常包含银行的敏感信息。一个智能客服的推理请求可能是："客户张三（身份证号310xxxxx）的账户余额为500万元，请生成产品推荐话术"。这些信息以Token的形式在整个链路中流转——从网关采集、到统计存储、到报表展示、到审计记录。

银行的数据合规要求是非常严格的：
- 客户个人隐私信息（姓名、身份证号、手机号、账户信息）不能以明文形式出现在非核心系统的日志和报表中
- 不同密级的数据有不同的存储和访问要求
- 审计记录必须完整但也不能包含明文敏感信息

当前的做法通常是两种极端：要么完全不记录Token内容（只记录Token数量），这样效能分析无法深入；要么全量记录（包括敏感信息），这样存在合规风险。没有一种方案能在"保留语义信息用于效能分析"和"脱敏保护隐私合规"之间取得平衡。

### 怎么解决

**第一步：在Token采集层进行实时敏感信息识别。** 模型网关在采集Token数据时，不是原样存储，而是经过一个轻量级的敏感信息识别引擎。这个引擎基于规则+模型的混合方式工作：

- 规则层：正则匹配身份证号、手机号、银行卡号等固定格式的敏感信息
- 模型层：用小模型（如NER命名实体识别）检测人名、地址、金额等非固定格式的敏感信息
- 分级层：根据工单的场景标签和业务方密级，确定该请求的数据密级（公开/内部/机密/绝密）

识别在Token流上进行，不需要重建原始文本——Token流中连续的几个Token如果被NER模型判定为"人名"，就直接在这些Token上打标签。

**第二步：语义保留脱敏——脱敏但不破坏效能分析。** 这是核心难点。传统的脱敏方式是直接替换成星号或占位符（如"张三"→"***"），但这会破坏Token计数和语义信息。我们的做法是：

- **人名脱敏**：保留Token数量和词性，替换为同类型的通用名（如"张三"→"客户A"），3个Token还是3个Token
- **金额脱敏**：保留数量级，模糊化精确值（如"500万"→"数百万"），Token数量可能不变或变化1个
- **身份证号脱敏**：保留前3位（地区码）和校验逻辑，中间位替换（如"310xxxxx"→"310****X"），Token数量基本不变
- **账户号脱敏**：保留开户行信息，账号部分替换

关键原则：**脱敏后的Token流在Token数量、Token序列模式、input/output比例等维度上与原始Token流保持一致**，这样基于脱敏后数据计算的TEE效能指标不会失真。

**第三步：按密级分层存储。** 不同密级的Token数据采用不同的存储策略：

| 密级 | 原始Token | 脱敏Token | 统计指标 | 保存期限 |
|---|---|---|---|---|
| 公开 | 可选存储 | 存储 | 完整统计 | 长期 |
| 内部 | 不存储 | 存储 | 完整统计 | 长期 |
| 机密 | 不存储 | 不存储 | 仅聚合指标 | 中期 |
| 绝密 | 不存储 | 不存储 | 仅资源用量 | 短期 |

"仅聚合指标"意味着只记录该次调用的总Token数量、延迟等数值，不保留任何Token内容（即使是脱敏后的）。"仅资源用量"更严格，只记录消耗了多少CU算力单位。

**第四步：脱敏可逆与审计追溯。** 对于机密及以上密级的数据，虽然日常不存储Token内容，但在安全审计场景下需要能够追溯到原始请求。我们设计了"脱敏信封"机制：

- 原始Token内容用AES-256加密存储在独立的加密库中
- 密钥由安全审计部门独立管理，平台无权访问
- 加密数据的索引（请求ID、时间戳、场景标签）存储在主库中
- 日常查询只能看到脱敏数据或聚合指标
- 安全审计时，审计部门授权后可用索引从加密库中检索原始数据

**第五步：脱敏质量校验。** 每次脱敏后自动进行质量校验：
- Token数量偏差检查：脱敏前后Token数量偏差不超过±2
- 语义完整性检查：脱敏后的Token流是否仍能反映原始请求的语义结构（如问答关系、多轮对话结构）
- 脱敏覆盖率检查：敏感信息识别的召回率是否达标（目标>99%）
- 误脱敏检查：非敏感信息是否被误判为敏感信息（目标误判率<1%）

### 核心创新点

1. **语义保留脱敏** — 脱敏时保持Token数量和语义结构不变，确保下游效能分析（TEE计算）不受影响
2. **Token流级别的敏感信息识别** — 不重建原文，直接在Token序列上做NER识别和规则匹配
3. **按密级分层存储策略** — 不同密级数据对应不同粒度的存储，平衡合规与分析需求
4. **脱敏信封机制** — 加密存储原始数据，审计时可追溯，日常不可见
5. **脱敏质量自动校验** — Token数量偏差、语义完整性、覆盖率和误判率的四维校验

### 与专利5的关系

专利5的TEE效能画像依赖于Token统计数据。本专利解决了"Token数据在流转过程中如何合规脱敏"的问题，确保专利5的效能分析可以在满足银行合规要求的前提下运行。两者是互补关系：专利5需要Token数据，本专利保证Token数据合规可用。

## 专利5、6、7的完整关系

```
专利5（度量层）：Token效能画像 + 容量评估
  → 解决"算力用得怎么样"
  → 需要 Token 数据作为输入

专利7（合规层）：Token流敏感信息脱敏
  → 解决"Token数据怎么合规流转"
  → 保证专利5的输入数据合规可用
  → 是专利5的前置条件

专利6（决策层）：SLA驱动的智能审批 + 动态规划
  → 解决"基于效能数据怎么做审批决策"
  → 消费专利5的TEE画像数据
  → 是专利5的下游应用
```

三篇形成完整链路：**合规可用（专利7）→ 效能量化（专利5）→ 决策优化（专利6）**
