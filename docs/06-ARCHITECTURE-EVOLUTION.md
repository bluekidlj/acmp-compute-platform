# 架构迭代经历

ACMP 的架构不是从一套完整产品模型一次设计出来的，而是在真实环境验证中逐步收敛。这个过程的核心不是不断增加概念，而是判断哪些职责属于平台，哪些应交给 Kubernetes、HAMi 和 Prometheus。

## 1. 从“大平台”回到一条主流程

早期设想包含工作空间、多层资源池、超分、复杂项目配额、训练、推理、监控、大屏和创新实验室。对象完整，但难以判断一项操作最终对应哪个 Kubernetes 事实。

第一轮取舍是确定单管理员 MVP：

- 先完成集群接入、资源池、规格、租户配额和推理服务；
- 暂不引入复杂审批、高并发和跨服务事务；
- 每个页面必须能追溯到数据库关系或 Kubernetes 对象；
- 演示功能与真实功能分开。

平台由此从概念展示转为可实际操作的控制面。

## 2. 把 Kubernetes 作为资源事实来源

集群、Node 和 GPU 最初容易被平台数据库重新建模，进而出现模拟数据残留、Node 已变化但平台仍显示旧设备等问题。

后续明确：

- Node 只展示 Kubernetes API 实际发现的对象；
- GPU 数量以 Kubernetes 可调度资源和设备插件元数据为依据；
- 数据库保存同步结果和管理关系，不凭空增加物理设备；
- 点击同步是重新读取事实，不是制造平台状态。

这一选择让 Docker Desktop、虚拟机 Fake GPU 和真实 GPU 集群能够使用同一条同步链路。

## 3. 从逐卡入池改为整机入池

逐张 GPU 加入独享池或共享池看似灵活，但会让同一台主机同时存在多种调度语义，还需要逐卡维护标签、规格和占用关系。

实际管理中，一个 Node 通常安装同一品牌、同一型号的 GPU。因此改为：

- 用户选择 Node；
- Node 上全部 GPU 一次性入池；
- 一个 Node 只属于独享或共享之一；
- 调度标签写在 Node；
- 规格按相同资源条件复用。

这次取舍显著降低了数据模型和 Kubernetes 调度的复杂度。

## 4. 区分物理 GPU、共享份额和 Node

共享池曾容易把 HAMi 上报的份额理解为更多物理 GPU，导致“一张卡显示成十张卡”。

最终概念被重新划分：

- 物理 GPU 数量不因切分改变；
- Kubernetes Node 数量不因切分改变；
- `1/4` 表示每张物理卡形成 4 个可调度规格份额；
- 多卡 Node 的总份额等于物理卡数乘以切分数；
- 共享规格节点数是业务容量，不是物理设备数。

页面和数据库由此可以同时表达设备事实与可分配能力。

## 5. 把切分职责交给 HAMi

平台最初可能在自身模型中描述 vGPU，但只有 Kubernetes 实际上报对应资源，Pod 才能被调度。

最终职责划分为：

- ACMP 选择目标 Node 和切分比例；
- ACMP 通过 Kubernetes API 修改 `hami-system` 中的节点级配置；
- HAMi device-plugin 执行切分并上报资源；
- Kubernetes Scheduler 完成调度；
- ACMP 同步并展示结果。

平台不模拟 HAMi，也不自己实现设备切分。这一边界同时兼容真实集群和未安装 HAMi 的独享测试环境。

## 6. 从固定规格改为按资源形成并复用规格

预置大量规格会出现与真实 GPU 型号不匹配、演示数据混入生产列表和同类规格重复的问题。

新的做法是：

- GPU 入池时根据真实品牌、型号、池类型和资源参数匹配规格；
- 有相同规格则复用；
- 无匹配时创建；
- 规格聚合多个来源 Node 的可用份额；
- 租户按规格获得配额。

这样，规格成为物理资源与业务配额之间稳定的合同，而不是人工维护的设备清单。

## 7. 让调度约束真正落到 Kubernetes

只在数据库中记录独享或共享，不能保证 Pod 调度到正确主机。

平台因此在 Node 入池时写入：

- 池类型；
- 算力规格；
- GPU 品牌和型号；
- 共享方式。

部署时，Pod 使用对应 Node Selector，并同时请求真实 GPU 或 HAMi 资源。数据库关系、Node 标签和 Pod 资源请求由此形成一条闭环。

## 8. 打通模型文件和镜像的内网链路

推理服务不仅需要 YAML，还受到两个大文件影响：vLLM 镜像和模型权重。

经过外网与内网验证后形成的 MVP 方案是：

- 镜像由 Harbor 或 containerd 离线导入提供；
- 模型权重预先放到 GPU Node 本地目录；
- 模型广场登记宿主机绝对路径；
- Deployment 通过 `hostPath` 挂载到容器；
- vLLM 参数引用容器内路径；
- 提交前展示完整运行配置，并打印生成的 YAML。

这个方案牺牲了跨 Node 自动迁移能力，但能以最少组件完成内网真实部署验证。

## 9. 从集群大图转向分层监控

监控页面最初试图在集群层展示全部曲线，数据密集且难以定位问题。

后续改为：

- 集群列表展示整体健康；
- 集群详情展示 Node 列表和关键指标；
- Node 详情展示平均值、单卡仪表盘和完整时间曲线；
- 资源管理页面不重复监控曲线；
- 无数据时保留空图，不使用 Mock 冒充真实指标。

监控结构由“看起来丰富”转向“能够下钻定位”。

## 10. 为内网运行补齐工程链路

平台在虚拟机和内网安装过程中暴露出镜像缺失、containerd namespace、磁盘压力、Nginx 权限、Java 缺失和日志不可追踪等问题。

这些问题推动工程形成：

- Windows 一键开发和清理脚本；
- Linux 前后端发布目录；
- 先停后起、PID 管理和健康检查；
- Logback 运行日志与启动日志分离；
- 监控组件外网下载、内网导入、安装和验证脚本；
- 自动扫描 ImagePullBackOff 并生成缺失镜像清单。

这部分不是平台领域模型，却决定了系统能否真正落地。

## 11. 当前架构结论

最终得到的不是一个自研 GPU 调度器，而是一层清晰的管理控制面：

```text
ACMP：资源关系、规格、配额、部署意图和运维视图
Kubernetes：容器编排、对象状态和 Node 调度
HAMi：共享 GPU 切分与资源上报
Prometheus 体系：指标采集、存储和查询
Harbor / containerd：镜像分发
Node 本地目录：当前 MVP 的模型文件存储
```

这个架构的价值在于职责可解释、组件可替换、主流程已经通过模拟和真实环境逐步验证。

## 12. 保留的演进原则

后续迭代继续遵循：

- 新概念必须对应明确的用户操作和底层事实；
- 不复制 Kubernetes 或 HAMi 已经承担的职责；
- 先完成单向主流程，再增加自动化和补偿；
- 页面展示真实数据，演示数据必须显式隔离；
- 内网可安装、可排错与功能实现同等重要；
- 优先扩展适配层和协议，不轻易拆分现有单体。
