# 1.3 资源池管理（Resource Pool）

平台固定维护两个资源池：

## 1.3.1 独享池

用于整卡调度。

特点：

* GPU独占
* 不进行切分
* 创建Pod时仅申请：

```yaml
limits:
    nvidia.com/gpu: 1
```

---

## 1.3.2 共享池

用于HAMI虚拟GPU。

特点：

* GPU共享
* GPU切分
* 创建Pod时自动生成：

```yaml
limits:
    nvidia.com/gpu: 1
    nvidia.com/gpumem: xxx
    nvidia.com/gpucores: xx
```

---

* Cluster

规则：

* 一张GPU同时只能属于一个资源池。
* 加入后就属于这个池子了，暂不提供修改功能

# 1.4 算力规格管理（Compute Flavor）

我建议把**算力规格（Compute Flavor）**定位成整个平台最核心的资源抽象对象，而不是简单的 GPU 规格。它代表平台向租户提供的一种标准算力套餐，包含 CPU、内存、GPU 资源及 GPU 使用方式（独享/共享），租户、项目和推理服务均通过算力规格申请资源，而不直接操作 GPU 或资源池。

---

# 1.4 算力规格管理（Compute Flavor）

## 1.4.1 功能说明

算力规格（Compute Flavor）是平台对计算资源的统一抽象，用于定义一套标准的资源配置。

每个算力规格包含：

* CPU 核数（CPU Core）
* 内存（Memory）
* GPU 数量（GPU Count）
* GPU 使用方式（独享 / 共享）
* GPU 型号（可选限制）
* GPU 切分比例（共享规格）
* GPU Core 比例（共享规格）
* GPU Memory 比例（共享规格）

平台所有资源申请均以算力规格为单位进行，租户、项目及推理服务均不直接申请 GPU。

---

## 1.4.2 算力规格分类

平台支持两类算力规格。

### （1）独享规格（Exclusive Flavor）

独享规格对应独享资源池。

特点：

* 使用整张 GPU。
* 不进行 GPU 虚拟切分。
* Pod 创建时仅申请 `nvidia.com/gpu`。
* 一张 GPU 同时只能被一个实例占用。

示例：

| 规格名称     | 资源池 | GPU型号 | CPU     | Memory | GPU   |
| -------- | --- | ----- | ------- | ------ | ----- |
| H20-独享-S | 独享池 | H20   | 16 Core | 64 Gi  | 1 GPU |
| H20-独享-L | 独享池 | H20   | 32 Core | 128 Gi | 1 GPU |
| A100-独享  | 独享池 | A100  | 32 Core | 128 Gi | 1 GPU |

部署时生成资源请求：

```yaml
resources:
  requests:
    cpu: "16"
    memory: "64Gi"
  limits:
    cpu: "16"
    memory: "64Gi"
    nvidia.com/gpu: 1
```

---

### （2）共享规格（Shared Flavor）

共享规格对应共享资源池。

特点：

* GPU 使用 HAMI 虚拟化能力进行切分。
* 每个规格定义 GPU 使用比例。
* 平台自动转换为 HAMI 所需资源参数。
* 多个实例可共享同一张 GPU。

示例：

| 规格名称 | 资源池 | GPU比例 | CPU     | Memory |
| ---- | --- | ----- | ------- | ------ |
| 小规格  | 共享池 | 10%   | 4 Core  | 16 Gi  |
| 中规格  | 共享池 | 20%   | 8 Core  | 32 Gi  |
| 大规格  | 共享池 | 50%   | 16 Core | 64 Gi  |

平台内部维护 GPU 切分参数：

| 规格  | GPU Core | GPU Memory |
| --- | -------- | ---------- |
| 小规格 | 10%      | 10%        |
| 中规格 | 20%      | 20%        |
| 大规格 | 50%      | 50%        |

创建 Pod 时，平台根据规格自动生成对应 HAMI 资源请求。

例如：

```yaml
resources:
  requests:
    cpu: "4"
    memory: "16Gi"
  limits:
    cpu: "4"
    memory: "16Gi"
    nvidia.com/gpu: 1
    nvidia.com/gpucores: 10
    nvidia.com/gpumem: 10
```

> 注：`gpumem`、`gpucores` 的具体资源名称以实际 HAMI 版本为准，平台负责完成规格到 HAMI 参数的映射，用户无需关注底层实现。

---

## 1.4.3 算力规格与资源池关系

算力规格必须绑定一个资源池。

```
算力规格
      │
      ├── 独享规格  → 独享池
      │
      └── 共享规格  → 共享池
```

平台根据规格所属资源池决定最终资源分配方式：

* 独享规格：从独享池分配一张完整 GPU。
* 共享规格：从共享池分配符合规格要求的 GPU 切片。

---

## 1.4.4 GPU 型号约束

为支持异构 GPU，算力规格支持配置 GPU 型号约束。

可选配置：

* 不限制（默认）
* H20
* A100
* 910B
* DCU
* 其他 GPU 型号

若配置了 GPU 型号，则平台仅从对应型号的 GPU 中进行调度。

若未配置，则允许调度到任意满足规格要求的 GPU。

---


## 1.4.6 算力规格使用流程

```
管理员创建算力规格
        │
        ▼
绑定资源池（独享池 / 共享池）
        │
        ▼
配置 CPU、Memory、GPU 参数
        │
        ▼
（共享规格）配置 GPU 切分比例
        │
        ▼
租户获得规格配额
        │
        ▼
项目创建推理服务
        │
        ▼
选择算力规格
        │
        ▼
平台自动生成 Kubernetes + HAMI 资源请求
        │
        ▼
提交调度运行
```

---


我建议**不要让规格直接绑定某一块 GPU**，而是**绑定资源池，并可选择是否限制 GPU 型号**。

这样做有几个优势：

* 规格不会因为某块 GPU 下线而失效。
* 后续新增同型号 GPU 后，规格容量会自动增加，无需修改规格。
* 支持异构资源池，同时保持规格模型稳定。
* 用户始终只面对统一的“算力规格”，不用关心底层 GPU 来自哪台机器、哪块卡。这样整个平台的抽象层次也更加清晰。

# 1.5 租户管理（Tenant）

管理员创建租户。

例如：

* AI研发中心
* OCR中心
* 风控中心

租户拥有资源配额。

配额分配对象：

不是GPU。

不是Node。

而是：

**算力规格。**

例如：

| 规格       | 数量 |
| -------- | -- |
| H20-独享   | 10 |
| H20-小规格  | 50 |
| A100-中规格 | 20 |

平台实时统计：

* 已分配
* 已使用
* 剩余
